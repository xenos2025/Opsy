# Opsy 客户运营交接手册 SOP

服务方交付给客户运营人员使用。目标是让接手人能找到资料、发起任务、检查结果，并在中断后继续工作。

配套文件夹：[客户项目交接模板](templates/customer-handover/README.md)。整份复制到客户项目后填写，内含项目登记、交付总清单、资料索引、遗留任务、验收签收及客户开工卡。

- 手册修订：2026-09-14，Asia/Shanghai。
- 编写依据：仓库提交 `9977442` 的 README、工作区合同、产品 / Blog / 数据流程、授权生命周期及任务结果合同；Opsy helper 本地帮助；Shopify 官方授权文档。
- 适用版本：Opsy `0.1.0` 当前源码。实际交付必须另填源码提交及安装副本核验结果，同版本号不代表内容一致。
- 验证范围：这是一份操作规范与签收模板，没有使用客户店铺或真实经营数据进行验收。文中的勾选项全部由交付双方按实际结果填写。

## 1. 先认识交付内容

Opsy 帮助以询盘、报价和业务联系为目标的 B2B Shopify 网站完成三项工作：商品上架与更新、Blog 发布与更新、服务方本地运营数据分析。客户用自然语言提出目标、提供材料和确认业务事实，Agent 整理文件、执行检查并保存结果。

客户不需要手写 JSON 或 GraphQL。企业画像、FAQ 和“本周三件事”用于支持上述工作。以购物车结账为主的 DTC 业务、多变体复杂编辑、订单退款、广告投放及网站技术审计应交给相应服务流程。

### 分工

| 角色 | 负责什么 | 交接时必须明确 |
| --- | --- | --- |
| 服务方交付负责人 | 安装核对、工作区配置、数据包、带教和问题排查 | 姓名、联系渠道、支持范围与约定响应时间 |
| 客户业务负责人 / 销售 | 确认参数、MOQ、交期、认证、客户群及真实询盘结果 | 哪些事实由谁确认，哪些仍待核实 |
| 客户运营人员 | 提交材料、选择任务、检查预览、跟进待办 | 主负责人、替补人员、项目位置 |
| 店铺管理员 / 发布审批人 | 店铺授权、权限处理和具体发布决定 | 由谁登录授权，谁有权批准草稿与发布 |
| Agent + Opsy | 整理、校验、执行已批准操作、回读和记录 | 输出真实完成状态及证据位置 |

一人可以承担多个角色，但每项待办必须指定一名实际负责人。手册中的支持安排由双方填写，不预设服务承诺。

## 2. 服务方交付前准备

### 2.1 建立客户交接登记

将本手册复制到客户自己的资料目录后填写客户信息；公共 Opsy 仓库只保留空白模板。

| 项目 | 填写内容 |
| --- | --- |
| 交付日期、时区 | 待填写 |
| 服务方负责人 / 客户运营负责人 / 替补 | 待填写 |
| 店铺管理员 / 发布审批人 | 待填写 |
| 支持渠道、服务范围、响应约定 | 待填写 |
| 客户项目根目录 | 待填写完整路径 |
| 运营工作区目录 | 从 `shopify-ops.json` 读取后填写 |
| 店铺永久域名 / 对外网站 | 待填写，由双方核对 |
| 宿主及版本 | Codex 或 WorkBuddy，填写实际版本 |
| Opsy 版本 / 源码提交 / 安装位置 | 待填写，附安装副本核验结果 |
| Node / Shopify CLI / API 版本 | 待填写实际环境与验证结果 |
| 已验收功能 / 尚未验收功能 | 分别填写，附证据位置 |
| 最近数据周期、时区、交付时间 | 待填写；无数据时明确记录 |
| 在途任务 ID / 最新结果目录 | 待填写；无在途任务则填无 |
| 客户资料备份位置 / 最近恢复检查 | 待填写，仅记录位置和结果 |

### 2.2 核对安装和项目

1. 服务方核对宿主、Node 和 Shopify CLI 可用，并确认客户实际加载的 Opsy 安装位置。仓库当前声明 Node ≥ 22.12；交付时以所交付版本的要求为准。
2. 按 [README 安装与更新说明](../README.md#安装与更新)预览安装计划，解释将修改的 Skill 安装目录，再由操作者确认执行。只安装客户使用的宿主。
3. 记录源码提交并核对安装副本。**拉取 GitHub 更新不会自动更新宿主中已安装的 Skill。** 当前同版本源码更新可能显示 `up-to-date`；需要强制更新时，由服务方核对源码后按 README 的 Force 流程预览、确认、安装，再重新加载宿主。
4. 打开客户项目，读取已有 `AGENTS.md` 和 `shopify-ops.json`。保留已有配置和目录；新项目先展示初始化方案，再确认创建。
5. 服务方检查客户资料备份和读取权限。客户应知道实际工作区在哪里，不能只收到软件安装包。

交付兼容性说明：仓库工具链仍声明 Shopify CLI `4.5.2` / Admin GraphQL `2026-07`；2026-09-13 的开发记录核对了 CLI `4.7.1`。这些历史记录不等于客户环境已通过实测。服务方须记录本次实际版本，并在客户环境验证所交付功能；版本兼容、真实授权或发布未验证时列入待办。详见[授权升级交接](handoffs/2026-09-13-opsy-cli-authorization-handoff.md)。

### 2.3 点交客户资料

下面除前两项外，路径均相对于运营工作区。新项目通常是 `shopify-ops/`，已有项目可能使用其他位置，必须以定位文件为准。

| 资料 | 服务方检查 | 客户接收标准 |
| --- | --- | --- |
| 项目根目录 `AGENTS.md` | 原有项目规则被保留 | 接手人知道业务和操作边界 |
| 项目根目录 `shopify-ops.json` | 能定位正确工作区 | 新会话能找到同一项目 |
| `config/store-profile.json` | 目标店铺、买家、市场、语言、卖家语气、询盘入口及负责人 | 业务负责人核对；未确认项明确列出 |
| `config/business-questionnaire.md` | 企业问卷及待确认项 | 客户可回答，确认摘要由 Agent 归入画像 |
| `config/buyer_faq.json` | 问题来源、答案确认状态及冲突 | 问题可用于选题，不把未经确认的答案公开 |
| `inbox/` | 产品、内容、FAQ、画像和数据材料可读 | 材料来源明确，产品与图片对应关系可确认 |
| `data-center/manifest.json` 及其声明文件 | 来源、日期、时区、提取时间、完整性 | 文件可校验；没有数据时保留有效空配置 |
| `data-center/archive/` | 有历史时保留历史文件及口径 | 能说明哪些周期可比；没有历史则注明 |
| `outputs/` | 草稿、预览、报告、结果和授权脱敏回执 | 在途任务结果能打开，待办可续接 |
| `backups/`、`ai-log/` | 写前备份和操作摘要 | 发生问题时能追到对象和操作 |

客户材料通过双方认可的受控渠道交付。不得把客户资料提交到公共 Opsy 仓库，也不交付密码、Token、Cookie、CLI 凭据目录或 OAuth 原始输出。不要仅靠 Git 克隆恢复客户项目：部分 `inbox/`、`outputs/`、`backups/` 文件默认被忽略，需另外核对并安全备份。Skill 独立安装，不复制到客户工作区内。

**本阶段完成条件：**登记表已填，客户能打开项目和关键文件，缺件均有负责人及补交日期。

## 3. 客户首次接收与带教

### 3.1 打开项目并检查状态

在已安装 Opsy 的 Codex 或 WorkBuddy 中打开服务方登记的客户项目，输入：

```text
使用 $opsy 检查这个项目，告诉我当前店铺、工作区位置、授权状态和缺少的资料。已有任务请列出任务 ID 和下一步。
```

客户核对目标店铺和工作区。若是新项目，先检查初始化预览；若是旧项目，让 Agent 沿用原配置。

| 显示状态 | 客户下一步 |
| --- | --- |
| 工作区未建立 | 与服务方核对目录并确认初始化方案 |
| 店铺连接未完成 | 完成连接引导，可先填写企业问卷、整理 FAQ |
| 轻量店铺建档未完成 | 补齐画像和业务配置，暂缓运营写入 |
| 授权未核验 / 需要恢复 | 由管理员配合完成授权检查或恢复 |
| 运营写入就绪 | 选择具体任务；该功能仍需通过自身检查 |

普通本地状态检查不能证明当前店铺授权有效。Agent 应实时核验目标店铺及权限，再决定允许的操作。

### 3.2 完成店铺授权

1. Agent 展示目标店铺、所需功能和权限用途，管理员核对。Opsy 默认计划覆盖商品、Blog、发布渠道和图片文件；扩展功能另行说明。
2. 确认本次权限计划，并选择是否允许以后自动发起相同计划的授权恢复。有效的既有同范围许可可以沿用。
3. 按 Shopify 浏览器页面要求完成登录与同意。Opsy 的自动恢复不能代替人员完成页面上的登录或同意。
4. Agent 重新检查实际店铺及权限，保存脱敏记录；客户只接收核验结论和下一步。

Shopify CLI 的 `store auth` 用于店铺授权及后续使用；实际应用权限可通过 `currentAppInstallation.accessScopes` 核验。依据：[Shopify store auth](https://shopify.dev/docs/api/shopify-cli/store/store-auth)、[应用授权范围查询](https://shopify.dev/docs/api/admin-graphql/latest/queries/currentappinstallation)。

**授权同意只解决访问权限。** 创建新商品或新文章时，还需先确认具体草稿操作，再在草稿核验后确认发布或排期；不得把授权同意视为内容发布批准。

### 3.3 完成首次带教

建议安排一次 45—60 分钟带教；这是建议安排，实际时间由双方确定。

| 环节 | 客户亲自完成 | 验收证据 |
| --- | --- | --- |
| 定位与状态 | 打开项目并核对店铺、资料和负责人 | 本次检查记录 |
| 业务确认 | 确认一组产品事实、受众、语言和询盘入口 | 确认记录及资料路径 |
| 商品演练 | 提交一份材料、检查字段预览，按实际意愿批准草稿 | 草稿 ID、后台预览、待补充项；未写入则记录本地准备 |
| Blog 演练 | 从可用数据或合格 FAQ 选题，检查本地预览 | 选题依据、预览和修改意见 |
| 数据演练 | 查看已交付数据的周期、缺口及行动建议 | 数据校验和分析文件；无包时记录待交付 |
| 任务续接 | 新会话按同一任务 ID 继续 | 能找到已有对象和未完成事项 |

仅演练并记录已具备前置条件的功能。没有真实执行的图片上传、草稿或发布项目标记“待验收”；如本次不需要公开发布，保留草稿，发布能力另约验收。

## 4. 日常操作：客户可以直接复制的话术

### 4.1 每次开工

```text
使用 $opsy 检查当前项目。先检查是否有相关在途任务，再建议今天可以推进的三件事，每件写明需要我提供什么、由谁负责、怎样算完成。
```

一次选择一个明确目标。已有任务先续接；新任务由 Agent 建立稳定任务 ID。客户材料可直接作为附件提交，由 Agent 放入对应资料目录。

### 4.2 商品上架与更新

**客户准备：**产品表或供应商材料、对应图片、目标市场和语言；对参数、MOQ、交期、价格、认证等承诺明确已确认项。图片外观不能证明规格或认证，供应商宣传也不自动成为本企业承诺。

```text
使用 $opsy 整理这批商品材料。先检查已有商品和重复项，展示产品分组、图片归属、缺失事实与建议标题。先准备草稿方案，等我确认具体内容再创建草稿。
```

1. 核对“哪些行是一个商品”、SKU、主图和图片使用权。复杂多变体组交服务方确认支持方式。
2. 确认面向哪类买家、主要用途、语言、询盘入口和页面落点，再审阅文案。搜索指标只用于需求判断，不能证明商品性能。
3. 检查逐项预览并选择本次候选。资料不齐时，可走最低填写草稿路径：核心事实与安全检查仍须通过，缺项列入待补充清单。
4. 批准指定商品的非公开草稿创建。Agent 写入并读取实际结果后，交付草稿 ID 和 Shopify 后台 / 店铺预览入口。
5. 客户在后台预览检查标题、正文、图片、参数、链接和询盘入口；补齐发布检查要求的内容。
6. 如需发布，再批准本次具体发布操作及渠道。Agent 核验发布状态和公开页面，保存结果。

现有商品更新应先读取现状，展示字段差异并保存写前备份，再按具体批准更新和回读。图片上传属于明确操作，文件上传成功后还需检查是否绑定正确商品并正常显示。

**完成条件：**每个商品有实际状态、已知 ID、预览或公开链接、字段核验结果和剩余事项。创建草稿不计为公开上架。

### 4.3 Blog 发布与更新

**客户准备：**业务画像、产品知识、可确认 FAQ、配图材料和希望引导到的产品 / 询盘页面。

```text
使用 $opsy 根据本项目有效数据和已确认 FAQ 提出 Blog 候选，说明依据、目标买家和页面落点。让我选题后再写正文并生成本地预览。
```

1. 查看选题依据：优先使用服务方有效 GSC + GA4 本地数据。新站可在有效空数据配置和合格 FAQ 问题基础上冷启动，必须标注“未观察到搜索需求指标”。两者均不满足时先补资料。
2. 确认题目、目标买家、语言、文章形式和承接页面。更新旧文时由 Agent 检查近期修改记录，按流程处理改写冷却期。
3. 检查本地预览：事实、结构、FAQ 答案、产品链接、配图对应关系和询盘 CTA。SEO 字段也一并检查。
4. 内容通过写入检查后，批准具体 Shopify 草稿创建；Agent 核验草稿和字段，客户检查实际呈现。
5. 确认具体发布或排期操作后执行。排期任务在公开状态实际核验前保留待核验状态。

**完成条件：**已确认选题有依据，内容与图片检查完成，草稿 / 发布状态准确，结果包能继续跟进。文章已发布不表示排名、流量或 AI 引用已提升，效果需以后数据验证。

### 4.4 数据导入、分析与询盘跟进

**客户准备：**服务方交付的数据包；确认周期与业务问题。客户无需配置 Google API 或提供 Google 凭据。

```text
使用 $opsy 检查这份服务方数据包，先说明来源、周期、时区、缺失项，以及准备归档、替换和新增的文件。确认导入后，再分析重点变化和下一步行动。
```

1. 服务方提供 manifest 及其引用文件；客户检查导入预览后确认，由 Agent 归档受影响旧文件、导入并校验。
2. 阅读报告中的来源、周期、提取 / 交付时间与缺失指标。没有指标应写“不可用”，不能用零或估算替代。
3. 历史比较先核对数据范围和周期是否可比；无法比较时说明原因，继续分析当前数据。
4. 联系点击、WhatsApp 点击和联系意图不能直接算真实有效询盘。业务负责人 / 销售核实实际线索结果，由服务方按约定交付分析数据。
5. 从报告中选择后续行动，明确负责人、完成条件和双方约定日期。详细结论保存在分析文件中。

**完成条件：**数据包通过校验，报告有证据和缺口说明，行动有人负责，真实询盘的确认责任明确。分析结果基于本地快照，不能称为实时 Google 数据。

## 5. 怎样确认任务真的完成

每次任务结束，要求 Agent 保存结果包，包括部分完成和受阻任务：

```text
<运营工作区>/outputs/runs/<task_id>/<run_id>/
  result.json   逐项状态、对象 ID 和证据
  report.md     完成内容、缺口和结果说明
  handoff.md    下一步、负责人和完成条件
```

客户通常先读 `report.md` 和 `handoff.md`。详细内容预览、数据分析、图片回执和核验证据由结果包链接到相应文件。

| 报告状态 | 客户如何理解 |
| --- | --- |
| 本地准备完成 `local_prepared` | 资料或文案已生成，尚不能声称店铺已有草稿 |
| 待资料 / 待批准 `pending_input` / `pending_approval` | 等待明确输入或具体操作决定 |
| 草稿已核验 `draft_verified` | Shopify 草稿已存在并回读，尚未计为公开发布 |
| 发布已核验 `published_verified` | 相关发布状态及公开页面已有核验记录 |
| 分析完成 `analysis_complete` | 本地分析已交付，后续业务行动仍可能待办 |
| 部分完成 `partial` | 按对象分别检查，不能把整批都算成功 |
| 待核验 / 失败 `pending_verification` / `failed` | 核对具体结果后再决定下一步，不直接重复创建 |

客户检查四项：实际完成数量、对象链接或文件路径、未完成原因、每项待办的负责人和完成条件。命令执行成功本身不能代替结果核验。

## 6. 中断、换人或换电脑时如何接手

1. 离开前保存当前结果、已知对象 ID、输入材料和待办。无法确定写入结果的对象标为待核验。
2. 接手人打开同一客户项目。换电脑时，由服务方通过认可渠道同步所需客户资料并逐项检查完整性；新电脑单独安装 Opsy 和运行环境，按需重新授权，不复制凭据或整个宿主运行目录。
3. 用同一任务 ID 续接，Agent 检查最新记录、输入变化和实时店铺状态。修改过的事实、图片或操作内容需要重新校验，原批准仅在范围仍适用时沿用。
4. 已知对象继续使用原 ID；超时但没有返回 ID 的创建操作先在店铺查询，确认实际结果后再决定重试。
5. 新结果使用新运行记录，保留旧记录及此前对象，不覆盖历史。

```text
使用 $opsy 继续任务 <任务 ID>。先读取最新结果与 handoff，核对已有对象、变化的材料和授权状态。结果不确定的操作先查店铺，再告诉我下一步。
```

若任务记录或证据丢失，先联系交付负责人恢复或核对店铺，不重新初始化旧项目来绕过缺件。

## 7. 常见异常与处理责任

| 情况 | 客户 / Agent 先做什么 | 下一负责人 / 恢复条件 |
| --- | --- | --- |
| 找不到 Opsy、Node 或 CLI 不可用 | 保留提示和当前资料，核对宿主及安装位置 | 服务方；安装和环境检查通过 |
| 显示错误店铺 | 停止写入，核对项目和永久域名 | 服务方 + 管理员；实际店铺核验一致 |
| 授权失效 / 缺权限 | 保留任务；按已确认计划恢复，完成浏览器所需操作 | 管理员；实际权限复核通过 |
| 权限拒绝 / 恢复仍失败 | 保存脱敏错误摘要和回执，不循环授权 | 管理员；权限处理并复核通过 |
| 网络错误 / 限流 | 保留结果，报告网络或限流问题 | 服务方；连接恢复后先回读中断对象 |
| 正在恢复 / 冷却中 | 等现有恢复结束，不启动或终止其他恢复进程 | 服务方；查明当前尝试结果 |
| 图片仍在处理 / 不显示 | 保留文件 ID 和回执，先查询处理与绑定状态 | 服务方；处理完成、绑定正确、预览正常 |
| 写入超时或没有成功响应 | 标为待核验，查询已有对象 | 服务方；确认结果后决定继续或重试 |
| 数据包无效 / 周期不一致 | 保留错误和来源，暂停使用无效数据作结论 | 数据交付负责人；修订包通过校验 |
| 事实不确定 / 产品图片错配 | 列出具体字段或文件，暂停受影响项 | 业务负责人；事实与图片归属确认 |
| 更新后异常 / 页面内容错误 | 保留差异、对象 ID、备份和结果，不批量重做 | 服务方提出修复方案；具体修复获批并回读 |

报障时提供：任务 ID、发生时间与时区、操作目标、错误摘要、最近结果目录、已知对象 ID、是否出现写入中断。截图先遮盖敏感内容，不发送密码、Token、Cookie 或完整授权输出。Opsy 的写前备份用于核对和修复，不代表具有自动一键回滚能力。

## 9. 服务方执行参考

客户无需执行以下命令。服务方 / Agent 使用实际安装的 Skill 路径和客户项目路径替换占位符；结果输入文件由 Agent 按合同生成，不要求客户编辑。

| 用途 | 命令 | 副作用 |
| --- | --- | --- |
| 本地状态检查 | `node <skill-root>/scripts/opsy.mjs status --project <project-root> --json` | 只读本地；不证明实时授权 |
| 展示授权计划 | `node <skill-root>/scripts/opsy.mjs auth-plan --project <project-root> --store <store.myshopify.com> --json` | 只读本地计划 |
| 实时检查授权 | `node <skill-root>/scripts/opsy.mjs ensure-auth --project <project-root> --json` | 连接 Shopify 查询，不主动发起恢复；CLI 管理自身凭据 |
| 开工检查与已批准恢复 | `node <skill-root>/scripts/opsy.mjs status --project <project-root> --live --recover --apply --json` | 连接 Shopify、保存脱敏元数据；匹配既有恢复许可时可能打开授权 |
| 续接任务 | `node <skill-root>/scripts/opsy.mjs resume-task --project <project-root> --task <task-id> --json` | 只读本地结果和证据变化，不重放远端操作 |
| 校验数据包 | `node <skill-root>/scripts/opsy.mjs validate-data --project <project-root> --json` | 只读本地数据 |
| 预览结果包 | `node <skill-root>/scripts/opsy.mjs record-task-result --project <project-root> --file outputs/task-result-r1.json --json` | 校验并预览；输入文件须已存在 |
| 保存结果包 | 上一条命令加 `--apply` | 写入本地三个结果文件；使用新 run_id，拒绝覆盖已有记录 |

首次权限同意及恢复记录按[授权生命周期](../skills/opsy/references/authorization-lifecycle.md)执行；上述开工命令不能代替首次许可。真实写入前核对当前官方 Shopify 契约及所选 API 版本。
